# Text fields: plan in the owner's order (2026-11-26), for owner review

Branch `warehouse-text-spec`. Specs: `text_fields_spec_2026-11-19.md` (method and decisions 19-T1 to 19-T13),
`text_fields.md` (measurements, production trace, section 0 reconciles the two). Replaces

Agreement with production is not correctness. No rule is accepted because it agrees with production.

- Printed rows: table number, row number in the table, the cells, each cell's column span and row span.
- Placements: for each tagged value, its row and cell, the text shown, and whether it is hidden.

Not held, and what slice P builds: which table is a schedule, which row is its header, a true column number for
each cell (spans resolved), and which heading rows sit above a position. Spans were checked on a test fixture
only (2026-11-19 spec, item 8); P measures them on real filings.

## Agent runs

- Subagents run by the controller. Sonnet and Haiku on the same bundles; the smaller is kept if it passes. Never
  Fable. Jev is not used (19-T5 stays undecided).
- An agent gets a bundle: no production values, no network. It returns a rule as data, never code.
- No agent accepts its own rule. A fund whose structural change is still uncovered stops at the build of record
  (19-T13); a new name in a known slot does not.

## Shared-model constraints and findings (owner, 2026-11-26; added after slice R's decisions)

A field's meaning is fixed by its relations to the other fields in one shared model, the same for every fund, not by
the label a filer's rule assigns. Cause: BCRED and HPS fixed rates were accepted as a spread because the filer files
them under the spread tag.

| # | Work | When |
|---|---|---|
| K1 | Rate constraints as dbt tests on the read model: a spread needs a reference rate; a floor needs a reference rate; a fixed rate has neither; all-in = cash + PIK; all-in near reference level + spread | Slice R phase 3 (running) |
| K2 | Reference-rate table (seed): name, currency, kind, successor, public series. Every code resolves to a row | Slice R phase 3 (running) |
| K3 | A reading blocked by a hard constraint is kept as a HELD value beside the field (marked with the constraint), not in the shared field and not dropped | Slice R, after phase 3 reports |
| K4 | Each stored test failure gets a stable id (fund, constraint, rule), one finding per rule, not per row | Slice R, after phase 3 reports |
| K5 | Currency constraint: a reference rate's currency matches the loan's currency. Measurement first, then a constraint | Slice R, after phase 3 reports |
| K6 | Decisions table keyed on the K4 id: state, evidence, who decided. Shape of production's `data/decisions/` (append-only); the warehouse writes to that store when it becomes the build of record, and keeps no second ledger | Part of slice 6, which already holds findings and the place to record an "ignored" decision (HANDOFF "Left for slice 6") |
| K7 | Agent routing: an agent with page access takes findings with no decision and proposes a filer rule, a row correction with evidence, a constraint or model change (owner only), or a disposition. It never edits a value to pass a constraint and never loosens one; a check it does not control, or the owner, accepts | With K6 |
| K8 | Map every constraint to production's ledger rule ids; a constraint that restates an existing rule takes its id (one catalogue, used on rules at acceptance and on rows as findings) | After phase 3 reports |
| K9 | Constraints for later fields: class and rate fields, class and amounts, lien and class, dates (medium: listed, not blocking); printed subtotals (P4); vocabulary tables for currency, class, industry | Slices C and I |
| K10 | Component reading (a rare shape built from known parts inherits their readings) | When widening beyond the five funds |
| K11 | Cross-fund comparison of the same loan (independent of any filer's tags) | Needs position matching between funds; not planned yet |

Rules for all of it: hard constraints are only those that follow from a field's definition; every constraint runs as
a count before it may block; a broken constraint never changes a value, drops a row silently or raises a ceiling;
real data that breaks a constraint changes the constraint or the model, naming the rows. dbt detects (tests, stored
failures); the decisions store remembers (id, state, history). A clean result means consistent, not correct.

## Not in this plan

Any change to production, its wrappers or its stores. Network access or SEC downloads. A model call inside a
build. Position ids and matching.
