# 0001902649 BlackRock Private Credit Fund - reading notes (sandbox l7b, 2026-10-10)

Read-only. Queries in `scratch/2026-10-10_read/0001902649/` (b1 to b15 .sql, `ctxfacts.py`). Dollar amounts in
whole dollars as filed unless marked K or M. ctx = XBRL context id.

## 1. Headline

- OPEN rate defect, answered exactly (section 2). On every loan with a PIK part the filer tags three rates:
  `InvestmentInterestRate` = the printed Total Coupon; `InvestmentInterestRatePaidInCash` = the cash MARGIN;
  `InvestmentInterestRatePaidInKind` = the PIK MARGIN. The extractor keeps PaidInCash as the rate (first fact of
  the column in document order wins) and throws the plain tag away; the finalizer then adds the PIK margin to it.
  No existing wrapper setting returns the coupon for these rows. The sister fund 0001834543 files the same three
  tags in the same order and its sandbox (s1c) publishes the same wrong figure, so it is not "unlike its sister".
- Totals tie to the filed investments figure in all 13 quarters (largest fair value gap 18,136). The small gaps
  that remain are sign errors in the filer's tags on undrawn rows (cost tagged positive where the page prints
  parentheses): exact in 5 quarters.
- No `source_encodings` block exists in this wrapper at all. Three settings are missing (section 6).

Arithmetic: 9.45 = 3-month SOFR about 3.69 + 2.63 + 3.13. So PaidInCash + PaidInKind is the total margin, never the coupon.

Where it goes wrong: `pipeline/bdc_filings.py` maps both `investmentinterestratepaidincash` and
`investmentinterestrate` to `interest_rate` and keeps the first non-empty fact per context ("Keep first non-None
value per column", about line 950). This filer writes PaidInCash before the plain tag, so `interest_rate` =
0.0263 with `interest_rate_concept = paid_in_cash`, and 0.0945 is lost before any setting is read.
`financial_conventions.py` then classes a PaidInCash-sourced rate as `cash` and publishes rate + PIK.

Which existing setting gives the printed coupon:
- `filed_rate_reading`: no. It is read only "where the tag does not name its own kind"; here the surviving tag
  is PaidInCash, which names itself cash. It WOULD fix the fully-PIK and mislabelled rows that already carry the
  plain tag (list below), and `all_in` is the right value: "Ref Fixed Spread 20.0% PIK Total Coupon 20.00%" tags
  rate 0.20 = PIK 0.20; "Spread 9.76% PIK Total Coupon 14.09%" tags rate 0.1409, PIK 0.0976.
- `printed_margin_reading: cash_plus_pik`: no. It changes basis_spread only, on rows tagged with a spread and a PIK
  rate; these rows carry no spread tag.
- `pik_only_tag_reading`: no. It applies to rows with a PIK tag, no plain rate tag and no spread; every row here
  has the plain tag in the filing.
- Needed (new, small): when a context carries both the plain tag and PaidInCash, keep the plain tag as
  `interest_rate` and treat PaidInCash as the cash margin (basis_spread = PaidInCash + PaidInKind, pik_rate =
  PaidInKind). Switch it by wrapper, e.g. `source_encodings.paid_in_cash_tag_reading: ["margin"]`, for
  0001902649 and 0001834543 (TPG Twin Brook in the backlog is the same defect). Then add
  `filed_rate_reading: ["all_in"]`.
